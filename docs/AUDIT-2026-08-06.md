# Sovereign Apps Technical Audit — 2026-08-06

## Verdict

The repository is an architecture prototype, not a functional template. It has
useful boundaries and names the right major surfaces, but its documented status
overstated implementation. It should remain `0.0.1` pre-alpha until the P0 gate
in `working/BACKLOG.md` is complete.

## P0 correctness gaps

1. **Dependency resolution is not reproducible.** There is no lockfile or pinned
   pnpm version. The RN bridge became available after the original audit, but
   React Native 0.81 remains paired with React 18 instead of its React 19 peer
   line, and the root install depends on peer auto-install behavior.
2. **The protocol does not compile.** `framing.ts` omits the
   `SovereignMessage` import. `SovereignTunnelTransport` implements a raw-byte
   interface with JSON-message signatures.
3. **Framing is not safe across normal stream fragmentation.** The read loop can
   discard an incomplete frame, does not reject zero/oversized incoming lengths,
   and parses unvalidated JSON.
4. **The desktop adapter targets the wrong native API.** Version 0.6.1 of
   `@momics/iroh-http-node` exposes a high-level `createNode()` API and a
   low-level handle API. The current wrapper treats the low-level
   `createEndpoint()` result as an object with endpoint methods and passes the
   wrong key option.
5. **Desktop startup is broken before networking.** Key storage attempts to
   create a directory with `writeFileSync`; the `start` script invokes Node
   rather than Electron; the app lifecycle does not handle normal Electron
   quit/activate behavior.
6. **The mobile package is not a runnable React Native app.** It has no native
   iOS/Android project or complete app bootstrap. Its local bridge interface does
   not match the public bridge source (`start`, `nodeId`, `connect`/`openSession`).
   The UI can report connected after the stub or after a caught error.
7. **Pairing is simulated.** The desktop sends a hard-coded acknowledgement
   nonce and marks signatures verified without verification. The mobile QR flow
   does not drive the network handshake, and neither side persists/revokes trust.
8. **The custom QR implementation cannot encode the normal payload.** It fixes
   QR version 3-L, has incomplete QR structure/format logic and crashes when the
   payload exceeds capacity. The mobile camera scanner is also only a text field.

## Security gaps

- Authentication is not enforced before application messages are accepted.
- The nonce generator falls back to `Math.random`; secure pairing must fail
  closed when a CSPRNG is unavailable.
- Signatures cover only the nonce, not protocol version, peer identities,
  transcript, requested capabilities, expiry or channel binding.
- QR payloads and LAN advertisements are cast from JSON without schema,
  bounds, version or address validation; the declared `zod` dependency is unused.
- Replay prevention, pairing expiry, one-time session state, capability
  attenuation, key rotation, revocation and secure storage are absent.
- Paired peers are kept only in memory and the desktop creates a dummy identity.
- The pairing renderer's `escapeHtml` functions replace dangerous characters
  with themselves, while peer-controlled fields reach `innerHTML`.
- No rate, concurrency or payload policies protect pairing/application handlers.
- Stub transports look operational, which can hide a fail-open deployment.

## Modularity and neutrality gaps

- Discovery, bootstrap, transport, session framing, authentication and app
  capabilities are mixed rather than exposed as independent adapters.
- `hubId`, `media.stream`, Music Hub references, PRISONS naming and comments
  aimed at one product make the template less neutral.
- The so-called WiFi-direct module only serializes UDP advertisement bytes. It
  neither sends nor receives UDP and is not Wi-Fi Direct in the platform sense.
- Music Streaming Hub's practical LAN mechanism is Bonjour/mDNS on desktop;
  its current mobile discovery is also incomplete. It should be treated as a
  source pattern, not proof that a generic module is ready.
- Bluetooth/BLE, NFC/deep-link bootstrap, transport preference, network-change
  handling and reconnect/fallback policies are absent.
- There is no module manifest, feature selection mechanism or generator for an
  adopter to choose modules.

## Open-source and release gaps

- The baseline originally had no independent Git repository or public remote.
- It declared MIT but had no root `LICENSE` file.
- Packages have no deliberate `exports`, `files`, publication scope or release
  policy; the `@sovereign-apps` npm scope may not be available to this owner.
- CI has no lockfile, dependency cache contract, OS matrix, native build, real
  tests, security checks or physical-device gate.
- The current landing shows simulated peers as connected. The intended output is
  instead an installable web-presence module plus a minimal Next.js integration
  example, not a project marketing/status site.

## Stable gate

Do not create a stable tag or release until all of the following are true:

- standard clean install succeeds from a committed lockfile;
- build, typecheck, lint and non-empty tests pass in CI;
- real Electron ↔ physical iOS and Android pairing succeeds from QR through
  authenticated bidirectional messages;
- direct LAN and relay paths are separately exercised;
- threat model and security tests cover replay, invalid QR, wrong fingerprint,
  unauthorized messages, revocation and key persistence;
- public packages or documented source-link workflow resolve without private
  state; and
- README/status claims match the verified support matrix.

SA-012 makes this gate executable: `scripts/release/generate-support-manifest.mjs`
is red for missing, stale, failed, unsigned or absent physical evidence. The
native workflow records blocked iOS/Android builds when their host projects are
not checked in; it never turns a skipped runner into support evidence.
